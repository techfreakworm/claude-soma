# PLAN — FI-DOMAIN: Caddy-via-own-domain file relay (basicauth, isolated)

Author: soma-improver. Date: 2026-05-31. Subject: implementation plan for the
FUTURE_IMPROVEMENTS.md Social sub-section "Caddy-via-own-domain file relay",
elevated to HIGH priority per user direction; replaces the prior auth-gated
path-suffix design with a basicauth-gated isolated subdomain design. Auth
model updated post-planning per user constraint: a single shared password
(`HERMES_FILES_PASSWORD`) gating the entire site via Caddy `basicauth`.

---

## TL;DR

- **URL shape:** `https://files.mayankgupta.in/<lead-name>/<file>` for operational
  use; `https://files.mayankgupta.in/pub/<uuid-slug>/<file>` for share-link
  semantics (12-hex UUID slug as depth-in-defense; `basicauth` is the primary gate).
- **Backend:** Caddy `file_server` — already running on the VPS; zero new process;
  native range-request support (resumable downloads) and sendfile(2) zero-copy
  for the large-binary case that triggered this work.
- **Directory layout:** `/var/lib/claude-soma/relay/<lead-name>/` for per-lead
  bundles; `/var/lib/claude-soma/relay/pub/<uuid-slug>/` for the share-link
  namespace (directory listing disabled for `/pub/*`).
- **Retention:** 7-day default via a new `claude-soma-relay-cleanup.timer` +
  `scripts/relay_cleanup.sh`; overridable via `HERMES_RELAY_RETENTION_DAYS`;
  `.pin` marker in a directory prevents deletion of that directory's contents.
- **Auth:** Caddy `basicauth` — one shared password sourced from
  `HERMES_FILES_PASSWORD` in `/etc/claude-soma/secrets.env`; bcrypt hash
  generated by `scripts/caddy-files-render.sh` at deploy time.
- **Migration timeline:** Phase 1 (Day 0) — Caddy block live, DNS pointing,
  `soma-relay` helper shipped; Phase 2 (Day 7) — audit and migrate hardcoded
  ngrok URL patterns; Phase 3 (Day 14) — stop markserv + ngrok processes.
- **Restart requirements:** none — `caddy reload` is graceful; no channel restart,
  no api restart, no frontend restart.

---

## Problem statement

The system currently uses ngrok for ad-hoc file relay: the `social-publish`
pipeline and similar workflows serve large files (images, pptx decks, video clips)
via markserv + ngrok (`https://51b26900ecba.ngrok.app/` and similar). On 2026-05-30
ngrok bandwidth limits were hit while relaying a 235 MB pptx for the demo video
campaign — the transfer was painfully slow and the tunnel was rate-throttled. ngrok
also presents a "Visit Site" interstitial to unauthenticated browser sessions that
breaks automated Medium import flows (Medium's embedding pipeline makes an
unauthenticated GET; the interstitial returns HTML instead of the image/file,
so embeds fail silently). The user's domain and VPS are already serving traffic
via Caddy; the fix is to use that infrastructure directly rather than routing
through a third-party tunnel.

---

## Why the prior FUTURE_IMPROVEMENTS recommendation is being revised

The prior design (shipped in commit `c7f501d`, FUTURE_IMPROVEMENTS.md Social
section "Caddy-via-own-domain file relay") recommended two things: (1) a
path-suffix endpoint `claude.mayankgupta.in/files/` rather than a subdomain,
and (2) Caddy `forward_auth` to the Next.js `/api/auth/check` endpoint (GitHub
OAuth gate) with a tokenized `/files/pub/<uuid>/` tier for public Medium assets.
That design was correct for the constraints it was solving: auth-gated access
reused the existing GitHub OAuth session cookie, and the path-suffix avoided the
cookie-scope problem that would have broken `forward_auth` on a subdomain. The
new user constraints flip both axes: files must be accessible behind a simple
shared password (not GitHub OAuth, and not public), and the serving mechanism
must be isolated from `soma.mayankgupta.in` and the admin web pages. With the
isolation requirement in force, a path-suffix on `claude.mayankgupta.in` is the
wrong shape — it shares the hostname, Caddy site block, TLS certificate, and
operational lifecycle with the admin app. The new plan uses a dedicated subdomain
(`files.mayankgupta.in`) served by a standalone Caddy site block with no
dependency on the Next.js app, plus Caddy `basicauth` with a single shared
password sourced from `HERMES_FILES_PASSWORD`. The prior survey's conclusion on
subdomain cookie scope (problematic for `forward_auth`) is no longer relevant
because `forward_auth` is gone. The rest of the prior design's analysis — the
`soma-relay` helper, fallback to ngrok, per-lead namespace, `/pub/<uuid>/` soft
obscurity — informed this plan directly.

## Section 1 — Subdomain vs new domain

### Candidates

**(a) `files.mayankgupta.in` (subdomain of the user's existing domain)**
One DNS A record pointing to the VPS IP. Caddy auto-issues a Let's Encrypt
certificate on the first HTTPS request once DNS propagates (~5–30 minutes,
depending on the registrar's TTL). The site config lives in the Caddyfile as a
separate `files.mayankgupta.in { ... }` block, fully independent of the
`soma.mayankgupta.in` block. Cookie scope is isolated by default — cookies set
on `soma.mayankgupta.in` do not flow to `files.mayankgupta.in` unless the
`Domain=.mayankgupta.in` attribute is explicitly set, which neither NextAuth.js
nor any other component in this repo does. Zero additional cost; the user already
controls `mayankgupta.in`.

**(b) `soma-files.com` or similar fresh domain (full isolation)**
A new registrar registration (~$12/yr). Full TLD-level isolation: `mayankgupta.in`
DNS problems cannot affect this domain. Caddy ACME still handles the cert
automatically. Extra cost, extra renewal to track, no meaningful security advantage
over (a) for a single-user personal VPS where TLD-level DNS hijacking is not a
realistic threat model.

**(c) Stay on `claude.mayankgupta.in/files/` (path-suffix from the prior plan)**
Rejected. Path-suffix shares the hostname, Caddy site block, cookie scope, TLS
certificate, and operational lifecycle with the admin app. This is the opposite
of isolated. A Caddyfile misconfiguration in the admin block could inadvertently
affect the files path; if the Next.js app on port 3000 crashes, a catch-all `handle`
block could intercept `/files/` requests. The prior plan chose path-suffix precisely
because it needed shared cookie scope for `forward_auth`. With `forward_auth` gone
and isolation required, the path-suffix choice collapses.

### Recommendation

**Candidate (a) — `files.mayankgupta.in`.** Provides genuine structural isolation
at zero additional cost. The isolation is not semantic: Caddy treats
`files.mayankgupta.in` as an entirely separate virtual host; the file_server
process has no code path that touches the Next.js app or the FastAPI dashboard.
If both application servers crash, `files.mayankgupta.in` continues serving files.

**DNS A record the operator must add:**

```
files.mayankgupta.in.   300   IN   A   <VPS_IP>
```

`<VPS_IP>` is the same IP as `soma.mayankgupta.in` (same VPS, same Caddy instance).
After adding the record, wait for DNS propagation before sending the first HTTPS
request to `files.mayankgupta.in` — Caddy's ACME challenge requires the DNS to
resolve to the VPS before it can provision the cert.

## Section 2 — Caddy site config snippet

The following block is added to `/etc/caddy/Caddyfile` after the existing
`soma.mayankgupta.in { ... }` block. The `$BCRYPT_HASH_HERE` placeholder is
replaced by `scripts/caddy-files-render.sh` at deploy time (see Section 6).

```caddy
files.mayankgupta.in {
    # PRIMARY GATE: single shared password (bcrypt hash substituted by
    # caddy-files-render.sh from HERMES_FILES_PASSWORD in secrets.env).
    basicauth /* {
        soma $2a$14$BCRYPT_HASH_HERE
    }

    # /pub/* namespace: directory listing OFF.
    # UUID slugs under /pub/ are opaque credentials; exposing a dir listing
    # at /pub/ would enumerate all active share tokens to any authed user.
    handle /pub/* {
        file_server {
            root /var/lib/claude-soma/relay
            hide .* index.html
        }
    }

    # Default: gzip/zstd compression for text assets; binary blobs (pptx, mp4)
    # are already compressed and are served unmodified (Caddy's encode directive
    # checks Content-Encoding before attempting compression).
    encode gzip zstd

    # All other paths: directory listing ON (password-gated, so only the operator
    # sees it). Lets the operator verify what is published per lead without
    # needing to SSH in or run soma-relay list.
    file_server browse {
        root /var/lib/claude-soma/relay
        hide .* index.html
    }

    log {
        output file /var/log/caddy/files-access.log {
            roll_size 20mb
            roll_keep 5
        }
        format json
    }

    header {
        # Prevent search-engine indexing of the relay content.
        X-Robots-Tag "noindex, nofollow, noarchive, nosnippet"
        # Private: auth-gated content must not be cached by shared proxies/CDNs.
        Cache-Control "private, max-age=300"
        # Strip the Server header (minor info leak reduction).
        -Server
    }
}
```

**Directive annotations:**

- `basicauth /* { soma $2a$14$... }` — gates every path under this site behind
  HTTP Basic authentication. Username `soma` (short, fast to type). The bcrypt
  hash is generated by `caddy hash-password` at deploy time; the plaintext never
  appears in any committed file. The browser caches the credential for the realm
  so the user is not re-prompted on every navigation within the site.
- `handle /pub/* { file_server { ... } }` — matched before the catch-all
  `file_server browse` block. `browse` is NOT enabled here; the UUID slug is an
  opaque access token and its parent directory should not be enumerable.
- `encode gzip zstd` — compresses text responses (markdown, HTML, JSON). For binary
  blobs Caddy skips compression automatically when the Content-Encoding is already
  set or the MIME type is non-compressible.
- `file_server browse` — for all paths outside `/pub/*`. The password gate makes
  directory listing accessible only to the operator; it allows in-browser
  inspection of what files are published per lead without SSH access.
- `Cache-Control "private, max-age=300"` — `private` is critical for auth-gated
  content; `public` would allow shared caches (CDNs, proxies) to serve the
  response to unauthenticated requests. 300 seconds is a short-lived browser
  cache that permits resumable downloads without stale-content risk.
- `X-Robots-Tag "noindex, nofollow, noarchive, nosnippet"` — prevents search
  engines from indexing relay content. Combined with the password gate, this
  keeps the relay off public indexes even if a search-engine bot somehow obtains
  the credential.

## Section 3 — Backend choice

### Candidates

**(a) Caddy `file_server`** (zero new process; native to the Caddy binary already
running; fastest path for binary blobs; range-requests and HTTP/2 built in; gzip
and zstd compression).

**(b) `markserv`** (renders markdown on the fly — already used in
`/tmp/social-engagement/` for the planning docs; SLOW for binary blobs; adds a
Node.js process; no range-request support; no HTTP/2).

**(c) Python `http.server`** (simplest possible fallback; single-threaded; no
compression; no range requests; no HTTP/2; known to stall under any concurrency).

### Recommendation

**Candidate (a) — Caddy `file_server`.** The user's primary pain point is
bandwidth (ngrok is slow for large binaries). Caddy's file_server uses
`sendfile(2)` on Linux for zero-copy kernel-space transfer — this is the fastest
possible mechanism for serving static files from disk. It supports HTTP range
requests natively, which means a partially downloaded 235 MB pptx can be resumed
without restarting from byte 0. HTTP/2 multiplexes concurrent transfers over a
single TLS connection. gzip/zstd compression reduces transfer size for text assets.
All of this is built into the Caddy binary already installed on the VPS; no new
process, no new dependency, no new language runtime.

markserv's value proposition is markdown-to-HTML rendering. The relay's primary
use case is binary artifact delivery (pptx, mp4, images). The planning doc
rendering currently done by markserv at `/tmp/social-engagement/` is a different
use case: those docs are consumed by the operator during a session and do not need
to be relayed to external viewers. If the user wants markdown rendering on
`files.mayankgupta.in` in the future, a pre-render step (generating HTML from .md
at publish time) or a sidecar markserv instance on a `/docs/` sub-path is the
right mechanism — that is explicitly out of scope for this plan (see Section 11).

Plain `.md` files served by Caddy `file_server` are delivered with
`Content-Type: text/plain; charset=utf-8`, which browsers render as monospace text.
This is acceptable for the relay's secondary use case (the operator inspects a
published planning doc); the relay is not a documentation site.

## Section 4 — Directory layout + ownership + retention

### Layout

```
/var/lib/claude-soma/relay/                    <- Caddy file_server root
├── README.md                                  <- explains the relay bundle layout
├── <lead-name>/                               <- per-lead namespace
│   ├── deck.pptx                              <- arbitrary artifacts
│   └── output.mp4
└── pub/                                       <- soft-obscurity namespace
    └── <12-hex-chars>/                        <- UUID slug directory
        └── <file>
```

Per-lead isolation prevents filename collisions: `output.pdf` and `diagram.png`
are both common default output names across leads. Cleanup after retiring a lead
is also simpler with a per-lead directory (one `rm -rf` rather than grepping for
all files from that lead across a flat namespace).

The `pub/` subtree uses the UUID slug as the namespace. Files in `pub/<uuid>/` are
never listable (Caddy `file_server browse` is disabled for `/pub/*`). The UUID slug
is generated by `soma-relay --public` at publish time; the caller receives the full
URL.

### Ownership

`ubuntu:ubuntu`, mode `0755` for directories, mode `0644` for files. The
`soma-relay` helper runs as the `ubuntu` user (no `sudo` needed). Caddy's file
server can read world-readable files regardless of which user Caddy runs as
(`caddy` or `www-data` on most installs). The `0644` mode is consistent with the
public-read intent of the relay.

`/var/lib/claude-soma/relay/` is created by `vps_bootstrap.sh` with the correct
ownership (see Section 9, implementation cost). Files placed there survive reboots
(this is `/var/lib/`, not `/tmp/`).

### Retention

**Recommendation: option (b) — custom systemd timer.** A new
`claude-soma-relay-cleanup.timer` running a `scripts/relay_cleanup.sh` script
daily at 04:15 UTC (right after the RC-URL refresh timer, before the daily-status
digest). This matches the existing pattern of `claude-soma-*.timer` routines in
the repo (`claude-soma-idle-reaper.timer`, `claude-soma-rc-url-refresh.timer`,
`claude-soma-secrets-backup.timer`).

systemd-tmpfiles (option a) is designed for `/tmp` and `/run`; using it for
`/var/lib` requires a custom `tmpfiles.d` rule and the per-subdirectory policy
flexibility is lower. The cleanup script is 20 LOC and gives the operator a single
obvious place to tune retention.

**Retention threshold:** 7 days (default). Files not modified in the last 7 days
are deleted. Env-var override: `HERMES_RELAY_RETENTION_DAYS` (read by
`relay_cleanup.sh` at runtime).

**Pin-file mechanism:** If a directory contains a file named `.pin`, the cleanup
script skips deletion of all files in that directory. This allows the operator to
mark specific lead bundles as long-term (e.g., a completed campaign's hero image
that is embedded in a live published Medium article). Creating the pin: `touch
/var/lib/claude-soma/relay/<lead-name>/.pin`.

**Timer schedule:** daily at 04:15 UTC. The time is chosen to avoid overlap with
the RC-URL refresh (`claude-soma-rc-url-refresh.timer`, which runs at ~04:00 UTC
per `99be0fd`) and the secrets backup (`claude-soma-secrets-backup.timer`).

## Section 5 — URL scheme

### Candidates

**(a) Human-readable:** `https://files.mayankgupta.in/<lead-name>/<file>` — easy
to navigate, debuggable, typeable. Enumerable: anyone who has the password can
guess other lead names (but with basicauth, they need the password first).

**(b) UUID slug per file:** `https://files.mayankgupta.in/<uuid>/<file>` — opaque;
harder to enumerate. Ugly for operational use; ops must query soma-relay to find a
file.

**(c) Hybrid (recommended):** `<lead-name>/<file>` as the default for operational
and internal use; `/pub/<uuid-slug>/<file>` as opt-in for share-link semantics —
used when the URL will be forwarded to a third party or embedded in a published
post.

### Recommendation

**Hybrid (c).** With `basicauth` gating the entire site, the primary enumeration
risk requires both knowing the password and guessing lead names. The `<lead-name>/`
namespace is human-readable for the operator and does not need UUID obfuscation for
its own protection. The `/pub/<uuid>/` namespace is depth-in-defense: it prevents
a user who knows the password (e.g., someone the operator shared credentials with
temporarily) from enumerating all share-link targets just by browsing the directory
tree at `/pub/`. The password is the gate; the UUID slug is defense-in-depth for
the share-link namespace specifically.

**UUID format:** `secrets.token_hex(6)` → 12 hexadecimal characters (48 bits of
entropy). Example: `4f2a8c3d9e01`. Sufficient to resist drive-by enumeration; short
enough to be manageable in URLs and log entries.

The `soma-relay --public` flag triggers UUID-slug publishing. The `soma-relay
publish` (no flag) uses the `<lead-name>/` namespace.

## Section 6 — Auth model

The relay is **NOT publicly accessible without authentication.** Caddy `basicauth`
gates the entire `files.mayankgupta.in` site behind a single shared password.
All other soft-obscurity layers (UUID slugs, robots block, access log, retention)
are defense-in-depth measures, not the primary gate.

### Password management

The shared password plaintext lives **only** in `/etc/claude-soma/secrets.env`
under the key `HERMES_FILES_PASSWORD`, file mode `0600`, owner `root:ubuntu`
(so the deploy scripts running as `ubuntu` can read it; the `caddy` process reads
it indirectly through the `EnvironmentFile=` in `caddy.service` — or via the
`caddy-files-render.sh` helper that reads it at deploy time).

**The plaintext value must never appear in any committed file, any commit message,
or any plan document.** Only the key name `HERMES_FILES_PASSWORD` is referenced
in code and documentation.

The operator can generate a strong password with:
```bash
openssl rand -base64 18
```
This is a suggestion for future rotation, not a requirement for the initial deploy.
The current value in `secrets.env` is the operator's choice.

### Deploy path: bcrypt hash generation

Caddy's `basicauth` directive requires a bcrypt hash, not plaintext. The hash is
generated at deploy time by `scripts/caddy-files-render.sh`:

1. Source `/etc/claude-soma/secrets.env` to load `HERMES_FILES_PASSWORD`.
2. Run `caddy hash-password --plaintext "${HERMES_FILES_PASSWORD}"` → outputs a
   `$2a$14$...` bcrypt hash to stdout.
3. Substitute the hash into the Caddyfile site block's `basicauth` directive via
   a sed in-place edit (or a heredoc rewrite of a template file).
4. Run `sudo systemctl reload caddy` for a graceful reload (no connection drops).

This script must be run once at initial deploy and again on password rotation.

**Username slug:** `soma`. Short, fast to type. Non-secret (the password is the
credential; the username is visible in the `Authorization` header but that is
normal HTTP Basic behavior).

### Defense-in-depth layers (secondary to basicauth)

| Layer | What | Why |
|---|---|---|
| Robots block | `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` | Prevents search-engine indexing even if a bot obtains the credential |
| Per-file expiration | Retention timer (Section 4) — default 7d, `.pin` override | Bounds exposure window; stale artifacts stop being accessible |
| Soft-obscurity slug | `/pub/<uuid>/` path (Section 5) | Prevents enumeration of share-link targets within an authed session |
| Access log | Caddy JSON access log at `/var/log/caddy/files-access.log` | Forensics if a credential leak leads to unauthorized downloads |
| Private cache | `Cache-Control: private` header | Prevents shared-cache (CDN/proxy) serving to unauthenticated requests |

**Explicitly NOT doing:**

- `forward_auth` to Next.js (per user constraint: no dependency on admin web pages)
- Per-user accounts or OAuth integration (single shared password is intentional;
  see Section 11 for V1.5 scope)
- Signed-URL tokens with expiry (the UUID slug plus the retention timer covers
  this use case adequately)
- Hot-link prevention via Referer check (the operator chose basicauth over
  per-URL tokens; Referer-based blocking adds friction without meaningful security
  improvement given the password gate)

## Section 7 — Migration from `/tmp/social-engagement/` (the ngrok bundle)

### Tooling: `soma-relay` helper (new)

A new CLI helper `scripts/soma-relay` (bash). Usage:

```bash
soma-relay publish <file>            # copy to <lead-name>/<file>; print URL
soma-relay publish --public <file>   # copy to /pub/<uuid>/<file>; print URL
soma-relay rm <url-or-path>          # delete the published file
soma-relay list                      # list current bundle for this lead
```

**Behavior:**

- Reads `SOMA_RELAY_DOMAIN` env var (default `files.mayankgupta.in`)
- Reads `SOMA_RELAY_ROOT` env var (default `/var/lib/claude-soma/relay`)
- Reads `HERMES_LEAD_NAME` (set by spawner at lead spawn; falls back to `general`
  if unset — e.g., when called directly by the operator from the shell)
- Auto-resolves `<lead-name>` namespace from `HERMES_LEAD_NAME`; `--public` flag
  generates a `/pub/$(python3 -c "import secrets; print(secrets.token_hex(6))")/`
  path and copies the file there
- Prints the full HTTPS URL to stdout on success; the caller stores or forwards it
- **Fallback:** if `SOMA_RELAY_DOMAIN` is unset or a HEAD check to
  `https://${SOMA_RELAY_DOMAIN}/` fails (DNS not yet propagated, cert not yet
  provisioned, or Caddy not yet reloaded), the helper falls back to the existing
  ngrok URL printing pattern and prints the ngrok URL instead. This preserves the
  current workflow during the cutover window at zero regression risk.

### Cutover timeline

**Phase 1 (Day 0 — this round):** Caddy block live, DNS A record added, bcrypt
hash generated via `caddy-files-render.sh`, `caddy reload` applied, `soma-relay`
helper installed. ngrok bundle (`markserv` + `ngrok` processes) continues running
as the fallback path. All NEW invocations of `soma-relay` use the Caddy relay.
Scripts and agents that currently call ngrok or markserv directly are NOT touched
in this phase.

**Phase 2 (Day 7 — next batch):** Audit scripts, agents, and skills for hardcoded
ngrok URL patterns and references to the markserv/ngrok bundle (see Section 8).
Replace with `soma-relay` calls. No operator signal required for this phase;
the migration can happen in a single commit.

**Phase 3 (Day 14):** Operator gives the go-ahead. Stop `markserv` and `ngrok`
processes. `/tmp/social-engagement/` becomes the local-only landing directory
(no public exposure). Bot's system prompt (`responsive_bot.md`) is updated to
stop mentioning the ngrok URL in DMs; `soma-relay` is the only file relay path.

The operator confirms each phase transition. Do not auto-advance.

## Section 8 — Impact on existing scripts hardcoding the ngrok URL

**Grep result (executed against `scripts/`, `agents/`, `skills/`):**

The grep for `51b26900ecba.ngrok.app`, `ngrok.app`, `ngrok.io`, and `ngrok`
found **no hardcoded ngrok tunnel URLs** in the scan targets. The only matches
were in `scripts/vps_bootstrap.sh` — lines 236–249, which are ngrok apt
installation boilerplate (the ngrok Debian package source, `apt-get install -y
ngrok`, and `ngrok --version`). These are installation steps, not hardcoded tunnel
URLs, and they are not affected by the relay migration.

This means Phase 2's audit will focus on RUNTIME patterns (scripts that call the
ngrok or markserv binaries to START a tunnel and then parse the resulting URL from
their output) rather than statically hardcoded URL strings. Likely candidates to
examine in Phase 2:

- Any script in `scripts/` that starts a `markserv` or `ngrok` process and captures
  its output URL. These will need to be replaced with `soma-relay publish` calls.
- `system_prompts/responsive_bot.md` — if the bot's instructions reference the
  ngrok URL pattern or instruct the bot to start markserv+ngrok for large file
  relay, that section needs updating to call `soma-relay` instead.
- The `social-publish` skill and its sub-agents (writers, posters) — the pipeline
  uses large file relay for hero images and video embeds. These are the primary
  consumers of the relay path; they are the highest-priority migration target in
  Phase 2.
- Any agent brief template in `agents/` that instructs a lead to start the ngrok
  bundle manually.

The Phase 2 commit should reference this plan as the migration guide.

## Section 11 — Out of scope

- Per-user account management (V1.5 if ever — single shared password is the
  intentional design; see Section 6)
- Markdown rendering on the relay (handle separately if the user wants rendered
  planning docs at `files.mayankgupta.in`; the relay's primary use case is binary
  artifact delivery)
- Per-lead-namespace disk-usage quotas / caps (V1.5 if abuse emerges — single-user
  VPS, realistic risk is near-zero)
- CDN or geo-distribution (single-region OCI instance; the user's audience is
  concentrated; CDN adds latency at the origin for the write path)
- HTTP/3 + QUIC enablement (Caddy supports it; explicitly enable later if needed
  for mobile clients; not a Day 0 priority)
- `markserv` removal from the VPS (stays as fallback permanently; removing it is a
  separate decision once the relay is validated in production through Phase 3)
- Subdomain wildcard cert (`*.mayankgupta.in`) to cover `files.mayankgupta.in` plus
  future subdomains — Caddy's per-site ACME provisioning is simpler and has no
  downside for the current scope
- Hot-link prevention via Referer check (password gate is the chosen mechanism;
  Referer-based blocking is bypassable and adds friction without real value)
- Signed-URL tokens with server-side expiry (UUID slug + retention timer covers
  the time-bounding requirement; server-side signing adds implementation complexity
  without proportional benefit for the single-user use case)
